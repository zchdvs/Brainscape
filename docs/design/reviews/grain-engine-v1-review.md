# Grain engine design v1 — adversarial review findings

> Three-reviewer adversarial pass over the v1 draft of [grain-engine.md](../grain-engine.md) (2026-08-30).
> 60 findings; the substantive ones are incorporated in v2 (see the doc's §13 Provenance).
> Kept as engineering record — the findings explain *why* v2 made the choices it made.

## Lens 1: DSP and arithmetic correctness

VERDICT: The doc's *bookkeeping* arithmetic is clean — I could not break it. DTCM 5+16+1+2+2+5+0.5+16 = 47.5 ≈ 48; AXI 48+8+19+10+8+16+20 = 129; SDRAM 16+23+23+0.5 = 62.5; 2^22 frames × 4 B = 16 MiB exactly and 2^22/48000 = 87.38 s ≈ 87.4 s; 23 MiB / 4 B / 48 kHz = 125.6 s ≈ 2 min (matches post-fx §6.1's own "~126 s"); CPU rows sum to 2,516–3,325 ("≈2,500–3,300") and 5,540 ("≈5,500"); tiers 8+24+32 = 64 = kMaxGrains; 65536/48000 = 1.365 s; 500 ms × ratio 4 = 96,000 > 65,536, so the 32.32 overflow argument is *correct* and the `65536/ratio` fallback clamp is dimensionally right. The failures are all in DSP semantics, not addition, and they cluster in three places. (1) **The write-head guards are wrong for reverse grains** — the doc simultaneously asserts "starting at the end of the source region" and "recedes from the write head, the safer direction", which cannot both hold; under the first, the near guard must be `d ≥ L·r + margin`, a whole grain length stricter than what is published, and a reverse grain at a short delay will read unwritten audio. (2) **The gain chain is broken in three independent ways that compound**: `1/√(N−1)` is applied to the unity-rate/Pattern/MultiDelay family where grains are provably *coherent* (at r=1 with zero spray every grain reads the identical source sample, so the sum is +18 dB at N=64, not 0 dB) — the corpus conditions √N on "spray/pitch/reverse decorrelate the grains" and the doc drops that condition; `window_gain = 1 + 2·shape` is Clouds' *smoothness* compensation attached to a field redefined as "flat-top amount", i.e. applied with the sign reversed (~15 dB of error across the front-panel Shape knob); and a movable `skew` fold point with an unnormalized triangle swings the grain peak by 12 dB over the macro's own [0.2, 0.8] range. Acceptance tests #2 (bit-exact null) and #3 (< 1 dB) cannot pass as written. (3) **The voice struct is insufficient for the vocabulary the doc ships**: `filt_z, filt_c` is a one-pole, but §5 and the CPU table both specify a per-grain resonant SVF and bit-crush, neither of which is representable; `env_inc = 2/width` is only correct for a symmetric fold; and the struct as printed is 68 B, not ~80 B. Separately, per-block normalization smoothing directly contradicts the doc's own block-splitting bit-exactness contract. Fix these before writing the render loop — several of them determine struct layout and the schema.

[HIGH] §3 Grain voice — Write-head guards / Reverse
CLAIM: "Reverse ... implemented as a negative increment starting at the end of the source region; reverse grains recede *from* the write head, the safer direction (§2.1)", guarded by `d ≥ L·max(0, r−1) + margin` and `d ≤ bufferLen − L·(1−r) − margin`.
PROBLEM: The two halves of that sentence are mutually exclusive, and neither published guard is valid for a reverse grain. If the grain starts at the END of the same source region a forward grain would use, its birth read position is W₀ − d + L·r, i.e. only (d − L·r) behind the write head, and the gap only grows from there — so the binding constraint is the near guard at t=0 and it must be `d ≥ L·r + margin`, a full L stricter than the published `L·max(0, r−1)`. Worked case: L = 500 ms (24,000 samples), r = 1.0, POS_LIVE base_ms small — the published guard admits d = margin, but the grain's read pointer starts 24,000 samples AHEAD of the write head and spends its whole life reading unwritten/stale ring content. Under the opposite convention (start at W₀ − d, recede), the near guard is fine and the claim 'safer direction' holds, but then the recession rate is (1+r), not (1−r), so the far guard must be `d ≤ bufferLen − L·(1+r) − margin`; at r=2 the published formula evaluates to bufferLen + L while the correct bound is bufferLen − 3L. Under either reading one of the two published formulas is wrong. The corpus carries the same defect (§2.1 hazard 2 writes (1−r) and then §3.7 says 'starting at the end'), so this is an inherited error the design doc did not catch, not a transcription slip. Secondary: the far guard also lacks the `max(0, ·)` its sibling has, so for forward grains at r>1 it evaluates above bufferLen and never clamps at all.
FIX: Replace both guards with a signed-increment derivation and publish it per direction. Let s = +1 forward, −1 reverse, and let p₀ be the birth read offset behind the write head. Forward: p₀ = d, near `d ≥ L·max(0, r−1) + margin`, far `d ≤ bufferLen − L·max(0, 1−r) − margin`. Reverse-from-region-end: p₀ = d − L·r, near `d ≥ L·r + margin`, far `d ≤ bufferLen − L − margin`. Reverse-from-anchor: near `d ≥ margin`, far `d ≤ bufferLen − L·(1+r) − margin`. Pick one reverse convention explicitly, state it next to the `offs` field comment (its signedness already implies the second), delete 'the safer direction' or scope it to the near guard only, and add both reverse cases to `ValidateMode()`'s guard-limit check alongside the forward one.

[HIGH] §3 Grain voice — Normalization; §10 tests #2, #3
CLAIM: "`gain = N > 2 ? rsqrt(N − 1) : 1` ... The `−1` and `> 2` guard keep a single grain at unity — a one-tap delay must not change level", combined with the Tu path making "the entire MultiDelay family and every ×1 Mosaic voice sound like a clean delay" and test #2 nulling Pattern A "to the bit".
PROBLEM: The √N law assumes incoherent grains. grain-delay-theory.md §3.6 says so explicitly and conditionally: "√N is the better model ... *because spray/pitch/reverse decorrelate the grains*". The design doc drops the condition and applies √N unconditionally — including to exactly the family where it provably fails. At r = 1.0 with spray = 0 (Pattern A, MultiDelay, every ×1 voice), a grain born at t_b has first_frame = W(t_b) − d and reads first_frame + (t − t_b) = t − d, independent of t_b: every concurrent grain reads the *identical* source sample at every output time. The sum is perfectly coherent, so the correct law is 1/N, and 1/√(N−1) over-shoots by N/√(N−1) — +9.6 dB at N=8, +18.1 dB at N=64. That breaks test #2 (null to the bit) and the doc's central 'sounds like a clean delay' claim for its own flagship family. Independently, the `−1` guard is unmotivated: plain 1/√N is already exactly unity at N=1, so the stated justification is false, and the guard instead creates a level bump — under the incoherent model output RMS = √N·gain gives 0.00 dB at N=1, +3.01 dB at N=2, +1.76 dB at N=3, +1.25 dB at N=4, +0.07 dB at N=64. Any mode whose density maps to 2–4 concurrent grains (target = 64·overlap³ ⇒ overlap 0.31–0.40) fails test #3's "< 1 dB output variation" on the normalization alone, before the window errors below are added.
FIX: Split the law by coherence rather than shipping one constant. Minimum: drop the `−1`/`>2` guard for plain `1/√N` (unity at N=1, monotone, removes the 3 dB bump). Better: normalize by the actual summed window energy, or interpolate the exponent — `gain = N^(−p)` with p ramped from 1.0 (coherent: unity rate, zero spray, zero pitch spread, zero reverse) to 0.5 (decorrelated), resolvable once per mode publish from spray_ms / spread_cents / reverse_prob / ratio-set width. Restate test #3 to sweep the whole N = 1…64 range, not just two endpoints, and add a coherent-case variant.

[HIGH] §3 Grain voice — Windowing
CLAIM: "`smoothness` crossfades raw-triangle↔LUT — boxcar↔triangle↔Hann on one cheap parameter. Exposed partikkel-style as **`shape`** (flat-top amount) ... Loudness is compensated by `window_gain = 1 + 2·shape` (§3.6)."
PROBLEM: Three different parameterizations are collapsed into one field and the gain formula ends up with the wrong sign. Clouds' `window_gain = 1 + 2·window_shape` compensates the *smoothness* axis: grain-delay-theory.md §3.4 says it "compensates the loudness change as the window narrows" and §3.6 says it corrects "a Hann-ish window has ~0.5 average value while a rectangular one has 1.0" — i.e. gain must RISE toward the Hann/narrow end. The doc redefines the field as "flat-top amount", which runs the opposite way: shape = 1 is then the boxcar, the window with mean 1.0 that needs no makeup at all, and the formula hands it ×3 (+9.5 dB); shape = 0 is then Hann, which needs ×2 (+6 dB) and gets ×1. That is ~15.5 dB of error across a knob the doc puts on the 8-knob performance panel (`macros.shape → layers.0.window.shape`, range [0,1]) and routes through a mode file whose example sets shape = 0.75. Separately, the described mechanism cannot deliver what the field name promises: the corpus's strategy-1 code (`gain += smoothness*(window − gain)`, `smoothness=0` → pure triangle, `=1` → LUT/Hann) morphs triangle↔Hann only — boxcar is unreachable by that crossfade, so "boxcar↔triangle↔Hann on one cheap parameter" overstates it (that phrase is Clouds' *manual* copy, quoted at corpus §4.1, not a property of the code excerpt at §3.4).
FIX: Decide which axis `shape` is and make the formula follow it. If `shape` is Clouds' smoothness (triangle→Hann), keep `window_gain = 1 + 2·shape` and change the prose from "flat-top amount" to "smoothness", dropping the boxcar end. If `shape` is genuinely partikkel's flat-top/`ksustain_amount` (which is what "sustain→1 yields a trapezoid" and the delay-mode argument actually need), add the flat-top mechanism (clamp/rescale the folded triangle before the LUT index) and invert the makeup to something like `window_gain = 2 − shape` (×2 at Hann, ×1 at boxcar), or better, divide by the window's own measured mean from the LUT. Cheapest correct option: store the window mean per (shape, skew) pair in the existing 4096-entry LUT's build step and divide by it.

[HIGH] §3 Grain voice — Voice struct / Windowing; §5 modifier vocabulary
CLAIM: `float env_phase, env_inc;   // env_inc = 2.0f / width_samples` together with "the envelope phase runs 0→2, folds at 1.0 into a triangle" and "`skew` (attack/decay fold point — percussive ↔ symmetric ↔ reverse-swell)".
PROBLEM: "Folds at 1.0" and "skew = fold point" contradict each other in the same paragraph. `env_inc = 2/width` is correct and preserves total duration for any fold point, so that part survives — but with the fold moved to s = 2·skew the unnormalized triangle peaks at s, not 1.0. Over the doc's own macro range (`window.skew` → [0.2, 0.8]) that is a peak of 0.4 to 1.6: a 12.0 dB level swing driven by the Shape knob, on top of the window_gain sign error above, guaranteeing test #3 fails. Correct normalization needs `tri = phase < s ? phase/s : (2−phase)/(2−s)`, i.e. two reciprocals — but the struct stores only `skew`, so this becomes two divides per sample per grain (≈2×14 cycles × 64 voices ≈ 1,800 cycles/sample) unless precomputed fields are added.
FIX: Replace `float skew` with two precomputed slopes resolved at birth — `float env_up, env_dn;` (= 1/s and 1/(2−s)) — or equivalently store the fold threshold plus the two reciprocals, and change the prose from "folds at 1.0" to "folds at `2·skew`, both legs normalized to unit peak". Add a unit test asserting peak envelope value == 1.0 across skew ∈ [0,1].

[HIGH] §3 Grain voice — Voice struct; §5 per-voice modifier vocabulary; §8 CPU budget
CLAIM: Struct field `float filt_z, filt_c;  // per-grain one-pole state/coeff (T0/T1 only)`, against §5's "SVF (LP/BP/HP/notch; fixed/random/LFO/envelope cutoff source), bit-crush (bits + decimation)", the mode file's `{"op":"svf","band":"lp","cutoff_hz":6000,"res":0.2}` inside `layers[].modifiers`, and the CPU row "Per-voice modifiers (32 single-pass SVFs, crush, glide)".
PROBLEM: The struct cannot hold either documented modifier. A resonant SVF needs two integrator states plus two coefficients (g/k or freq/damp) — 16 B — not one state and one coefficient; `res: 0.2` and the `band` selector have nowhere to live. Bit-crush needs a decimation phase counter and a held sample; neither exists. So four of the five listed per-voice modifiers (SVF, crush; and glide is T0-only) are unrepresentable in the voice as specified, and Blocks D / Interrupt D ("crush 5-bit") and Tunnel ("random BP") in the coverage acid test cannot be built. Anyone implementing from this header writes a one-pole, then discovers the schema and three factory modes need an SVF. The CPU row is inconsistent in the same direction: ~400 cycles ÷ 32 SVFs = 12.5 cycles/voice/sample, which is roughly a single-pass SVF's own cost by post-fx §3.1's op count (~14–18 ops single-pass) with nothing left over for the crush and glide the row also claims to cover.
FIX: Either (a) demote §5 and the JSON to a per-grain one-pole (drop `res`, drop `band`, rename the op to `lp1`/`hp1`) and fix Tunnel/Blocks/Interrupt in the acid test, or (b) widen the struct: `float svf_g, svf_k, svf_ic1, svf_ic2;` (+8 B over filt_z/filt_c) and `uint16_t crush_mask; uint8_t decim_n, decim_i; float decim_hold;` (+12 B). Then re-derive the modifier CPU row: 32 single-pass SVFs at ~10–14 cyc ≈ 320–450, plus crush on up to 64 voices, gives ~450–700 nominal, not ~400.

[HIGH] §3 Normalization vs §10 contract #1
CLAIM: "one-pole smoothed at 0.01 per block (§3.6)" alongside contract #1: "Rendering 4096 frames as `{1, 7, 32, 48, 64, 127, 512}`-frame blocks produces identical samples."
PROBLEM: These cannot both hold. A per-block smoother's time constant is a function of how the host chops the stream: at 0.01/block the corpus's ~100-block constant is 100 ms at 48-frame blocks, 2 ms at 1-frame blocks, and 1.07 s at 512-frame blocks — so the same 4096 frames rendered at the seven block sizes contract #1 enumerates produce seven different gain trajectories and seven different outputs. Clouds gets away with it because its block size is fixed; this design makes block size runtime (`numFrames` "1..maxBlockSize, varies freely") and then tests bit-exactness across it. The doc already spotted the analogous hazard for the RNG ("counter-based, keyed on absolute sample index") and did not carry the reasoning to the smoother. Any other per-block state (density phasor bookkeeping, `intermittency` draws, the STOCHASTIC self-limiter if it samples once per block) has the same problem.
FIX: Make the smoother sample-rate-referenced, not block-referenced: `coef = 1 − exp(−1/(τ·sr))` with τ ≈ 100 ms fixed, applied per sample (or per `kChunk = 16` sub-block, which is block-size-independent by construction since kChunk is internal). Add a line to contract #1 stating that no smoother, phasor, or RNG may key off block count or block boundaries, and add a test that renders the same input at two block sizes and diffs the normalization gain trace specifically.

[MEDIUM] §3 Grain voice — Write-head guards; §2 feedback topology
CLAIM: "**Write-head guards**, clamped once at schedule time (grain-delay-theory.md §2.1): `d ≥ L·max(0, r−1) + margin` ... and `d ≤ bufferLen − L·(1−r) − margin`."
PROBLEM: grain-delay-theory.md §2.1 names *three* hazards; the doc implements guards for two. Hazard 3 — "Feedback re-injection. If the granular output is written back into the same buffer, a grain can read material it produced microseconds ago — a tight, unstable loop" — is the one that applies hardest here, because §2.3 commits to topology A (tamed wet summed into the record buffer) and the schema places no floor on `position.base_ms`. At r = 1.0 the published near guard admits d = margin, so a mode with base_ms = 0 and feedback 0.35 forms a comb of period `margin` samples inside the feedback loop — a very high-Q resonance the 6.5 kHz taming lowpass only partially bounds. Contract #4 (feedback boundedness) tests ±12 st at max feedback but not the short-delay case that actually triggers this.
FIX: Add a third guard, `d ≥ d_min_feedback` whenever `feedback.amount > 0`, with d_min_feedback on the order of a few ms (state the number), and enforce it in `ValidateMode()` rather than only clamping at schedule time. Extend contract #4 to sweep `base_ms` down to 0 at max feedback.

[MEDIUM] §9 `dsp/` core API — Latency
CLAIM: `uint32_t WetOnsetLatencySamples() const noexcept;  // ≈ grain length + block; informational`
PROBLEM: This transcribes grain-delay-theory.md §2.2's figure, which is derived for `position = 0` under an end-of-region convention, into a design that uses a start-of-region convention with a nonzero delay. Under this doc's own POS_LIVE(d) semantics ("`d` behind the write head") the input sample at time T reappears at T + d + L·(1−r), so the correct expression is d + L·max(0, 1−r) + block, and at r = 1 it is simply d + block — the grain length drops out entirely. For the doc's own worked mode (Mosaic D: base_ms 250, size_ms 180, ratio set including 1.0) the reported figure would be ~180 ms + block against an actual ~250 ms + block; for a mode with base_ms 1000 the report is off by nearly a second. Since §12 item 8 makes wet-latency reporting a live product question and §9 calls the number informational-but-published, shipping the wrong formula is a user-visible defect.
FIX: Change the comment and the implementation to `≈ base_ms + size_ms·max(0, 1−r_min) + maxBlockSize`, resolved from the active ModeBlob, and note that the value is mode-dependent and changes on PublishMode. State the position convention (start-of-region) once in §3 next to the guards so §2.2's end-of-region figure is not re-imported elsewhere.

[MEDIUM] §9 EngineConfig vs §4 density law vs §10 contract #6
CLAIM: `uint32_t historyFrames = 1u << 22; uint32_t maxGrains = 64;` as runtime config, against "Density is overlap-referenced with a cubic law: `target = kMaxGrains · overlap³`", the fixed 8/24/32 tier split, and contract #6: "the same mode file drives firmware and plugin to identical output for identical input."
PROBLEM: `maxGrains` is a runtime field but the density law is written against the compile-time `kMaxGrains`, and the tier table hardcodes 8/24/32 summing to exactly 64. A plugin built with maxGrains = 128 running the same mode file gets `density: 0.55` → 21 concurrent grains instead of 10.6, a materially different texture and a different normalization gain — so modes are not "shared between pedal and plugin byte-for-byte" in behavior, and contract #6 fails by construction. The same applies to `historyFrames`: the far guard `d ≤ bufferLen − …` clamps differently on a smaller ring, so a mode with a long `base_ms` silently renders at a different delay. Nothing in the doc says these fields are pinned or that mode files record what they were authored against.
FIX: Either pin `maxGrains` and `historyFrames` as build constants shared by both targets and delete them from EngineConfig, or make the density law and tier split derive from the runtime value (`target = maxGrains·overlap³`, tiers as fractions 1/8, 3/8, 1/2) and add `authored_max_grains` / `authored_history_frames` to the mode schema so `ValidateMode()` can reject or rescale. Amend contract #6 to state which EngineConfig fields must match for the identical-output guarantee to hold.

[MEDIUM] §8 CPU budget — grain render row
CLAIM: "Grain render, 64 voices, tiered, mitigations | 1,280–1,600 | 3,200 (cache ×2) | grain-delay-theory.md §5.4"
PROBLEM: Two problems. First, 1,280 is the corpus's cache-hot, zero-miss arithmetic-only figure, which grain-delay-theory.md §5.3 introduces and then immediately labels: "This looks trivially affordable — **and that number is a lie, because of cache**." Using it as the low end of a *nominal* range re-imports the number the corpus retracted. Second, the miss model is rate-dependent and the doc's ×2 pessimism does not cover its own parameter range. Misses per grain per output sample = r/8 (32-byte line ÷ 4 B per interleaved stereo int16 frame). At r = 1 that is the corpus's 8 misses/sample × 40 cyc = 320. At r = 4 (+24 st — which is literally in the Mosaic D ratio set in §5's own JSON example) it is 32 misses/sample × 40 = 1,280 cycles from misses alone, giving ~2,560 nominal before any set-aliasing factor, and ~3,840 with the same ×2 conflict multiplier the doc applies — above the published pessimistic 3,200. Cubic Hermite's 4 taps can also straddle two lines, adding a second miss at boundaries for T0 grains.
FIX: State the rate assumption on the row. Publish the nominal as 1,600 (r ≈ 1, misses included) rather than 1,280–1,600, and recompute the pessimistic column at r = 4 with the conflict multiplier: ~3,800–4,000, which moves the pessimistic total to ~6,100–6,300 (61–63%) — still inside budget, but stop calling 3,200 the worst case. Add the ratio-4 scattered-position case explicitly to the §10 contract-#8 stress test.

[MEDIUM] §8 CPU budget — footnote
CLAIM: "UI/MIDI/LED and coefficient recalc (`sinf`/`powf`) run at control rate and are not charged."
PROBLEM: False for the grain engine, and the exemption hides a real cost. Everything the doc resolves "at birth" runs at *grain rate inside `Process()`*, not at control rate: `ratio = SemitonesToRatio(st + cents/100)` (an exp2/powf), equal-power pan `gain_l/gain_r` (cos+sin), `env_inc = 2/width` (a divide), and — per §5 — a per-grain SVF cutoff from a `random` or `LFO` source, which post-fx §3.1 verifies costs one `sinf` plus one `powf` per coefficient update. Grain birth rate = target/size: at 64 voices and 20 ms grains that is 3,200 births/s (~27 cyc/sample at ~400 cyc/birth, negligible), but the corpus's size range starts at 1 ms — at 64 voices and 1 ms grains it is 64,000 births/s ≈ 530 cyc/sample, comparable to the entire reverb row, and `burst` (count 3–8 per trigger, per Blocks/Strum B) multiplies it further. None of this appears in the table.
FIX: Add a "schedule-time resolution" row with a size-dependent range (e.g. ~30 cyc/sample at 20 ms grains, ~530 at 1 ms), and narrow the footnote to UI/MIDI/LED and *mode-level* coefficient recalc only. Budget the mitigations the row implies: a semitone→ratio LUT and a pan LUT alongside the existing 256-entry grain-size LUT, which would cut the per-birth cost several-fold.

[MEDIUM] §3 Grain voice — Phase format
CLAIM: "Bare float32 is separately ruled out — it loses sub-sample precision past ~2^24 samples on a multi-minute buffer (§3.3)."
PROBLEM: The threshold is quoted faithfully from grain-delay-theory.md §3.3 but does not apply to this design's own buffer, so as written the rebuttal is unsupported. The history ring is 2^22 = 4,194,304 frames = 87.4 s — below 2^24 (and below "multi-minute": 87.4 s is 1.46 min). Read literally, the doc's own numbers say float32 would be fine here. The real objection is stronger and different: float32's ULP is 2^(e−23), so anywhere in [2^22, 2^23) the spacing is already 0.5 samples — i.e. only one bit of sub-sample resolution at the top of this exact ring, and none at all in the 2-minute looper region. Degradation is progressive from ~2^17 upward, not a cliff at 2^24.
FIX: Restate as: "float32 absolute positions have ULP = 2^(e−23), so at the top of a 2^22-frame ring the spacing is 0.5 samples — one bit of sub-sample resolution, and none beyond 2^24. Fixed point keeps precision constant everywhere." Note in passing that the objection would be weaker if the phase were kept grain-relative (ULP ≈ 0.011 samples at 96,000), which is the actual reason the corpus recommends "fixed-point *or* a split integer+fractional representation".

[MEDIUM] §3 Grain voice — Phase format fallback
CLAIM: "(Fallback if measurement shows a material cost: 16.16 with grain length validated against `65536 / ratio` in the mode validator — a documented limitation, never a silent wrap.)"
PROBLEM: The formula is right for a single fixed ratio and wrong for every mode the schema can actually express. (a) `ratio` is not a scalar: the pitch `set` holds up to 8 entries, so the bound must use max over the set — for Mosaic D's `{−12, 0, +12, +24}` that is 4.0, giving 341 ms, not the 500 ms the size range allows. (b) `spread_cents` multiplies it (±10 c → ×1.0058) and `glide_st_per_s` means the ratio varies over the grain's life, so the endpoint ratio can exceed the birth ratio. (c) The bound is in *samples* but the schema mandates "Every time value is milliseconds or tempo divisions, never sample counts", and `modes::Validate(const ModeBlob&)` has no sample rate in its signature — at the plugin's 96 kHz the same 341 ms becomes 171 ms, so a mode that validates on the pedal wraps in the plugin. (d) A uint32 16.16 phase cannot represent a negative grain-relative offset, so the reverse convention has to be pinned before the fallback is even implementable.
FIX: Write the bound as `size_ms ≤ 65536·1000 / (sr · r_max)` where `r_max = max over pitch.set of ratio × (1 + spread_cents/1200 headroom) × glide endpoint`, pass sample rate into `Validate()` (or add it to ModeError as a precondition), and state which sample rates a mode file is certified for. Keep the note that this is fallback-only.

[MEDIUM] §10 Contracts and acceptance tests #2 and #3
CLAIM: "**Unity-rate null test.** A mode configured as Pattern A (density 1, ratio 1.0, no spray) nulls against a reference delay line to the bit." and "**Level consistency.** Sine sweep, density 1 vs. max: < 1 dB output variation."
PROBLEM: Both tests are unrunnable as written. (a) "density 1" collides with the doc's own cubic law: `target = kMaxGrains · overlap³` means density = 1.0 is 64 concurrent grains, i.e. maximum — so test #3 reads as "max vs. max" and test #2's Pattern A is specified at full polyphony rather than one tap. (b) A bit-exact null needs the reference delay to be int16-quantized identically (the wet path passes through the int16 ring, and §12.3 adds TPDF dither on write, which is stochastic), needs window ≡ 1.0 across the grain with COLA at the scheduled hop, needs `window_gain` ≡ 1 and normalization ≡ 1, and needs `pan_spread` = 0 giving gain_l = gain_r. With the normalization and window_gain defects above, the null is off by up to ~+9.6 dB at N = 8; even after they are fixed, the dither alone makes bit-exactness impossible.
FIX: Say "overlap such that N = 1" (or give the numeric density that yields one concurrent grain, ≈ 0.25) in both tests, and split the density-naming collision by renaming the JSON key to `overlap`. Restate #2 as a null to a stated floor (e.g. < −90 dBFS) against an int16 delay line with dither disabled, or scope the bit-exactness claim to the *read path* (Tu integer copy) rather than the full output.

[MEDIUM] §3 Interpolation tiered table; §5 mode schema; §5 Validation
CLAIM: Tier table: T0 = 8 voices with "cubic Hermite, per-grain stereo, glide, per-grain one-pole filter"; T1 = 24 with "linear, per-grain stereo"; T2 = 32 with "linear, precomputed pan". `ValidateMode()` rejects "out-of-range voice weights" and guard violations.
PROBLEM: Mode-declared features silently vanish past the tier limits and neither the schema nor the validator can see it. Glide is T0-only, so a Glide mode (PERIODIC trigger, `glide_st_per_s` set) whose density exceeds 8 concurrent grains renders 9…64 with no glissando — the effect's defining feature — and Glide D is specified as *two* layers of opposite directions sharing the 64 slots, so it hits the ceiling immediately. Per-grain filtering is T0/T1-only (32), so Tunnel's "random BP" and Interrupt C's "LFO→cutoff" degrade to unfiltered past 32 voices. Nothing in the mode file expresses "this mode requires ≤ 8 tier-0 voices", and §5's validation list does not mention it. [MEDIUM] §3 Voice struct; §7 Memory plan DTCM row
CLAIM: "**Voice struct (~80 B)**" with the 18 listed fields, and "64 grain structs (~80 B) 5" KiB in the DTCM table.

(a) The struct as printed is 68 B, not ~80: seven int32/uint32 (28) + env_phase/env_inc (8) + shape/skew (8) + gain_l/gain_r (8) + glide_inc (4) + filt_z/filt_c (8) + two uint8 (2) = 66, padded to 68. 64 × 68 = 4.25 KiB, so the table's 5 KiB implies 80 B and over-reserves. ## Lens 2: Real-time safety and platform reality

VERDICT: The architecture is sound and unusually well-traced to its corpus, but the real-time contracts are not yet safe to build from. Three classes of defect dominate. First, the concurrency story is asserted rather than specified: PublishMode's "single release-store swap" has no reclamation protocol behind it, so a second mode switch inside the trail window overwrites a blob the audio thread is still reading; ConsumeOnsetFlag is a test-and-clear across an ISR boundary with no atomicity; and nothing in the API says which thread may call SetParam, Trigger, PublishMode, or ActiveMode, even though SetParam's sampleOffset implies a lock-free event queue that is never described. Second, the bit-exactness contracts fight the rest of the document: the mandatory normalization smoother is specified "per block" (both split-variant and block-size dependent — the exact bug class §5 names as its own cautionary tale), the counter-based RNG's "absolute sample index" is undefined under transport jumps, freeze, and simultaneous draws, and cross-platform "identical output" is unreachable without an FP-determinism contract that would cost the FMA throughput the §8 budget assumes. Third, several platform numbers do not survive contact: maxBlockSize=48 / an accumulator sized for 256 / a contract that renders 512-frame blocks are three mutually exclusive figures; the 2 KiB T0 staging ring is 3–16x undersized; Init's "clears Bulk" quietly means a multi-hundred-millisecond 62.5 MiB SDRAM wipe (and a destroyed user loop on any plugin re-prepare); the 23 MiB looper-B clear at each overdub gesture has no owner; and the QSPI XIP risk is understated in a way its stated ITCM fallback cannot cover. Separately, the one worked JSON example in the schema section violates the document's own write-head guard, and §3 and §5 disagree on whether such a mode is clamped or rejected. None of this invalidates the design bet; all of it should be fixed in the doc before code is written against it.

[HIGH] §5 Hot-loading and mode switching; §9 PublishMode
CLAIM: "JSON parses off the audio thread into a ModeBlob double-buffer slot; a single release-store pointer swap publishes it... in-flight grains finish under the old blob, new grains are born under the new one — click-free by construction."
PROBLEM: A release-store swap makes publication race-free but says nothing about reclamation, and there are only two slots. The design explicitly keeps the old blob live for the lifetime of in-flight grains (§12.9: "up to one grain length of old mode", i.e. up to 500 ms at the top of the recommended size range). A second PublishMode inside that window has only one place to compile into — the slot the audio thread is still dereferencing — so the main thread writes over live data mid-render. Two footswitch presses 300 ms apart, or a MIDI program-change sweep, trigger it. ActiveMode() has the mirror problem: it hands a raw const ModeBlob* to a caller with no lifetime guarantee, so a UI thread holding it across a publish reads a half-rewritten blob. There is no epoch counter, no grain-population refcount, no retire queue, and no statement that the audio thread signals when the last old-blob grain dies. Note §7 budgets 16 KiB of AXI for a double-buffer of a ~1.6 KiB struct — enough for ~10 slots, i.e. the memory to fix this is already reserved.
FIX: Specify the reclamation protocol: N>=4 blob slots in a ring, each grain carrying a blob_epoch (or a per-blob active-grain count decremented at grain death), and a reuse rule of "a slot may be reused only when its epoch has zero live grains AND is not the published epoch". Have PublishMode return false (or block off-thread) when no slot is retirable rather than clobbering. Replace ActiveMode() with a scoped accessor that pins an epoch, or return a value-copied summary. State the memory ordering used (release on publish, acquire on the audio-thread load) and where the load happens (once per block, before scheduling).

[HIGH] §3 Normalization; §10 contract 1; §6 Automation semantics
CLAIM: "gain = N > 2 ? rsqrt(N - 1) : 1, one-pole smoothed at 0.01 per block (§3.6). ... The smoothing is mandatory." alongside contract 1: "Rendering 4096 frames as {1, 7, 32, 48, 64, 127, 512}-frame blocks produces identical samples."
PROBLEM: A per-block one-pole is definitionally not split-invariant: 4096 frames rendered as 8x512 applies the pole 8 times; as 4096x1 it applies it 4096 times. The two statements cannot both hold. The corpus is quoted correctly (grain-delay-theory §3.6 does say "a 0.01 coefficient at block rate is a time constant of ~100 blocks") — Clouds could do that because its block size is fixed; this design makes block size runtime-variable at the API. Worse, a per-block coefficient means the smoothing time constant varies ~10x in wall-clock between the firmware's 48-frame blocks and a host's 512-frame blocks, and again with sample rate. That is precisely the failure mode §5 names as its own cautionary tale ("never sample counts... DaisySP's own pos_ < 4800 bug"), committed one section earlier. The same objection applies to any per-block parameter smoother behind §6's "post-chain parameters smooth continuously", which a block-rate pole is not.
FIX: Respecify every smoother as a per-sample one-pole whose coefficient derives from a time constant in milliseconds and the runtime sample rate (a = 1 - exp(-1/(tau_ms*0.001*sr))), computed once at init. Document ~100 blocks @48 frames ~= 100 ms as the intended tau so the sound is preserved. Add an explicit rule to §10: "no engine state may be updated at block or chunk granularity", and note that the 7- and 127-frame cases in contract 1 exist specifically to catch kChunk=16 alignment leaks.

[HIGH] §10 contract 1 (counter-based RNG); §9 ProcessContext, SetFreeze
CLAIM: "Forced consequence: the scheduler's RNG is counter-based, keyed on absolute sample index — never a stateful stream advanced per call."
PROBLEM: "Absolute sample index" is never defined and every candidate definition breaks something. (a) If it is ProcessContext::timelinePos, a stopped transport freezes the key, so every grain draws the same spray, pan, ratio-select, reverse coin-flip and intermittency roll — the texture collapses while the user auditions with the transport stopped, which is the normal way people use a granular plugin; a DAW loop also replays byte-identical "randomness" every pass, and a scrub teleports the sequence. (b) If it is an engine-internal free-running counter, contract 6 ("identical output for identical input") and contract 7 ("SaveState -> LoadState restores byte-identical behavior") both fail unless that counter is saved, which SaveState's const signature and the state schema never mention. (c) Freeze compounds it: if the counter derives from the write head or the pinned anchor, SetFreeze(true) freezes the RNG and every frozen grain becomes identical. (d) Most concretely, keying on sample index alone means two draws at the same index return the same number — but the vocabulary produces simultaneous draws: burst {count: N, spacing_ms: 0} is legal in the schema, and a 2-layer mode fires both layers on the same CLOCK tick. Those grains get identical spray, pan and pitch selection, collapsing the stereo image exactly where the design wants width.
FIX: Define the key as a tuple hashed through a counter-based PRNG (Philox/Squares-style): (engine_sample_counter, layer_index, burst_ordinal, draw_purpose), where engine_sample_counter is a free-running int64 owned by the Engine, advanced by numFrames every Process regardless of transport state, and included in SaveState. State that it is independent of timelinePos and of freeze. Enumerate draw_purpose (spray, pitch-select, detune, pan, reverse, intermittency, jitter) so two draws in one grain birth never collide. Restate contract 6 as "identical for identical input and identical starting sample counter".

[HIGH] §9 EngineConfig; §7 memory plan; §10 contract 1
CLAIM: uint32_t maxBlockSize = 48; with the DTCM table budgeting "block accumulator 2ch x 256 x f32 = 2 [KiB]", while contract 1 renders "{1, 7, 32, 48, 64, 127, 512}-frame blocks".
PROBLEM: Three incompatible numbers. Process is contractually numFrames <= maxBlockSize, so with the shipped default of 48 the 64/127/512-frame cases in contract 1 are illegal calls and the test as written cannot run. If maxBlockSize is raised to 512 to make the test legal, the accumulator must be 2x512x4 = 4 KiB, not the 2 KiB budgeted, and the T0 staging rings scale with it too. The 256 in the memory table matches neither the config default nor the test. This is not cosmetic: PlanMemory is the pure function firmware and plugin both size their arenas from, so a wrong maxBlockSize is a silent buffer overrun on the first oversized block a DAW delivers (hosts routinely hand out 1024 or 2048).
FIX: Pick one worst case and propagate it. Recommend maxBlockSize = 512 as the config default (firmware passes 48; the plugin passes the host's maximum), write the DTCM accumulator row as a formula (2ch x maxBlockSize x f32) rather than a literal, and restate contract 1's block list as "all <= maxBlockSize". Add an explicit statement that Process with numFrames > maxBlockSize is UB (or add a debug assert).

[HIGH] §5 JSON example (mosaic.d) vs §3 write-head guards vs §5 Validation
CLAIM: The flagship schema example declares position {base_ms: 250, spray_ms: 40}, size_ms: 180, and pitch set [{-12},{0},{12},{24}]; §3 states the guard d >= L*max(0, r-1) + margin; §5 states ValidateMode() rejects "grain-length x ratio combinations that exceed guard limits".
PROBLEM: The example violates the guard. At +24 st, r = 4.0 and L = 180 ms, so the guard demands d >= 180 x 3 = 540 ms behind the write head; the mode declares 250 ms (down to 210 ms with negative spray). The read pointer therefore overtakes the write head partway through every +24 st grain and reads not-yet-written audio. Beyond the arithmetic, §3 and §5 prescribe two mutually exclusive remedies for exactly this case: §3 says the guard is "clamped once at schedule time" (silently moving the grain's position, changing the sound), §5 says the validator rejects the mode outright — which would make Mosaic D unloadable, the mode §3 names as "{-12, 0, +12, +24} *is* Mosaic D". Add the formula (base_ms >= size_ms * (max_ratio - 1)) to §5's validation list so mode authors can compute it, and add a matching acceptance test.

[HIGH] §12.7 risk register; §7 memory plan
CLAIM: "QSPI XIP stall during preset save (firmware runs BOOT_QSPI): a save's erase/write **may** stall instruction fetch. Test early; fallback is the audio ISR in ITCM." and, in §7, "the 8 MB QSPI holds only the parameter/mode blob, saved on explicit gesture (blocking, no wear leveling)."
PROBLEM: Three problems. (1) "May" is too weak: a NOR flash cannot service memory-mapped reads during an erase or program, so under BOOT_QSPI any instruction fetch that misses I-cache during a save stalls until the operation completes. The corpus puts that at "tens of milliseconds" for a 4 KB sector and "several hundred milliseconds" for a 64 KB block (post-fx §4.7), against a 1 ms ISR deadline — a guaranteed dropout, possibly a watchdog reset, not a risk to measure. The corpus also verifies PersistentStorage<T>::Save() is blocking with "\todo - Make Save() non-blocking" still open. (2) The fallback is under-scoped: relocating the audio ISR to ITCM is necessary but insufficient, because everything the ISR calls must also be resident — the grain render, the templated tier dispatch, the reverb, CMSIS-DSP's FFT — plus .rodata (FFT twiddle tables are flash-resident per the corpus). ITCM is 64 KB total. (3) §7 contradicts §12.7: under BOOT_QSPI the firmware image itself lives in QSPI from the bootloader's 256 KB offset, so QSPI does not hold "only the parameter/mode blob". Relatedly, §7's "AXI SRAM (512 KB, ~480 usable after bootloader)" misreads the corpus — the ~480 KB figure is the program-size cap for BOOT_SRAM apps, not a data-region reservation under BOOT_QSPI.
FIX: Rewrite the risk as a design constraint: mute or ramp down audio for the duration of a QSPI save, or move the parameter/mode blob to the microSD card the design already requires from v1 and reserve QSPI for firmware only. If the ITCM route is kept, budget it explicitly (list the functions and rodata to relocate against 64 KB) and add a measured-stall gate to §10. Fix §7 to say QSPI holds the firmware image plus optionally a small settings blob, and either drop the "~480 usable" figure or re-derive it for the boot mode actually chosen.

[HIGH] §10 contracts 6 and 7
CLAIM: "the same mode file drives firmware and plugin to identical output for identical input" and "SaveState -> LoadState restores byte-identical behavior across firmware and plugin."
PROBLEM: Bit-identical float output across arm-none-eabi/Cortex-M7 and x86-64 is not free and conflicts with the rest of the design. GCC defaults to -ffp-contract=fast, so a*b + c compiles to a single VFMA on the M7 (one rounding) and to separate mulss/addss on a non-FMA x86 baseline (two roundings) — different results, propagated and amplified through a feedback loop the design deliberately runs at up to 1.05 gain. The corpus's own normalization reference is fast_rsqrt_carmack, an approximation that differs from any sqrtf/rsqrtss path. Add sinf/powf/tanf from two different libms at grain birth and the builds diverge on the first grain. Making them identical requires -ffp-contract=off, a shared bit-exact transcendental/rsqrt implementation inside dsp/, and no fast-math — which directly costs the FMA throughput the §8 budget assumes ("single-cycle single-precision FMA" is load-bearing in the corpus's 15-25 cyc/grain/sample estimate).
FIX: Split the contract in two: (a) within one build, bit-exact under block splitting and state round-trip (contract 1, and a per-platform version of 7); (b) across builds, null to a stated tolerance (e.g. < -120 dBFS RMS over a 10 s render) rather than "identical". If true cross-platform bit-exactness is genuinely wanted, say so, list the price (-ffp-contract=off in dsp/, in-tree rsqrt / SemitonesToRatio / window LUT with no libm dependency, no fast-math), and re-derive the §8 budget without FMA contraction.

[HIGH] §2 signal path (LOOPER); §7 memory plan; §9 Init
CLAIM: "LOOPER (separate SDRAM buffers A+B, 4-way record/playback tap matrix)" and "looper A (committed) 23 MiB + looper B (overdub/undo) 23 MiB", with the only clearing statement being Init(...) "does NOT allocate; clears Bulk".
PROBLEM: The corpus design being adopted (post-fx §4.3) requires Buffer B to be "cleared to silence when overdub starts", and cleared again on undo — a 23 MiB memset at a footswitch gesture, with audio running. At the corpus's ~400 MB/s theoretical SDRAM peak that is ~60 ms; realistically 100-200 ms, i.e. 60-200 consecutive missed 1 ms deadlines if done synchronously in the control path. The design never mentions it; the only clearing contract is at Init. The same corpus section also specifies an overdub commit pass (A[i] += B[i] over 23 MiB) which it explicitly parks "outside the audio ISR" — the design drops that constraint too. This is the most likely source of a shipping-firmware dropout, and it lands on the feature (undo) cited as Microcosm parity.
FIX: Add a background buffer-maintenance service to the design: an incremental clear/commit that processes a bounded slab per audio block (e.g. 64-256 KiB, budgeted in §8), driven from the main loop or a low-priority task, with a state machine so a second gesture during an in-progress clear is queued rather than reentrant. Alternatively avoid the clear entirely with a per-buffer generation stamp plus a b_valid_until write watermark, making undo O(1) ("stop mixing B in, reset the watermark") and letting B be overwritten lazily as recording proceeds. Either way state the mechanism and charge it in §8.

[MEDIUM] §10 contract 2; §3 Windowing, Normalization

[MEDIUM] §3 Voice struct and tier table; §5 Per-voice modifier vocabulary; §7 DTCM
CLAIM: The struct has exactly "float filt_z, filt_c; // per-grain one-pole state/coeff (T0/T1 only)" and no other modifier state, at "~80 B"; §5 promises "Per-voice modifier vocabulary (<= 4 slots, all cheap, all resolved at birth): SVF (LP/BP/HP/notch...), bit-crush (bits + decimation), sub-octave ratio entry, glissando, gain."
PROBLEM: Two mismatches. (1) The struct cannot hold the advertised vocabulary. [MEDIUM] §9 Init / Reset; §7 "SDRAM is not zeroed at boot"
CLAIM: bool Init(const EngineConfig&, const Arenas&) noexcept; "does NOT allocate; clears Bulk" and void Reset() noexcept; "silences tails; keeps params+mode".
PROBLEM: "Does NOT allocate" reads as cheap, but "clears Bulk" is a 62.5 MiB SDRAM memset — at the corpus's ~400 MB/s theoretical peak ~165 ms, realistically 0.3-0.6 s of boot time that nothing in §7 or §8 budgets. Two consequences the doc never draws. (1) On the plugin, hosts call the prepare/Init path on sample-rate change, device switch, and often on transport stop/start; a contract that clears Bulk therefore silently destroys the user's recorded loop at moments they did not initiate. (2) Reset() has no RT-safety annotation at all, unlike SetSampleRate which does. For a granular delay, "silences tails" plausibly implies clearing the 16 MiB history ring (otherwise unfreezing or raising feedback after Reset resurrects old audio) — which is 40-80 ms and cannot happen inside Process. As written a caller cannot tell whether Reset is safe to call from the audio thread.
FIX: Split the contract: Init clears only the history ring and engine state; add an explicit ClearLooper() the host calls deliberately, and document that a plugin's prepare path must not call it. Annotate Reset() as RT-safe and define it as "kill all grains, zero post-chain/feedback/diffuser state, leave the history ring intact", with a separate non-RT ClearHistory(). [MEDIUM] §9 SetSampleRate and PlanMemory
CLAIM: MemoryPlan PlanMemory(const EngineConfig&) noexcept; "pure; callable before any allocation" where EngineConfig carries double sampleRate, alongside void SetSampleRate(double sr) noexcept; "not RT-safe; call while stopped".
PROBLEM: The two are inconsistent. PlanMemory's result depends on sampleRate — the reverb tank, the modulation delay lines, and the feedback diffuser are all specified in milliseconds and therefore sized in samples by the rate — so mutating the rate after Init invalidates arenas the caller already sized and handed over, with no re-plan path and no way for Init's bool to report it. Separately, historyFrames is a fixed frame count, so SetSampleRate silently rescales the ring's duration (2^22 frames = 87.4 s at 48 k, 43.7 s at 96 k) and with it every base_ms-to-frames conversion and both write-head guards. That is the pos_ < 4800 bug class the doc itself names in §5, expressed in the C++ API rather than the JSON. Finally, "call while stopped" is honest for a plugin but meaningless for the pedal, which the doc pins to 48 kHz for v1 anyway — so the method exists only to serve the case it cannot safely serve.
FIX: Delete SetSampleRate and follow the corpus's own recommendation (vst doc: "the plugin wrapper must re-call Init() whenever the host changes sample rate"): make rate a member of EngineConfig only, changeable solely by re-running PlanMemory + Init with fresh arenas. If a lighter path is wanted, make it bool SetSampleRate(double) returning false when the new rate would exceed the planned arena sizes, and state which sub-blocks it retunes. Either way document that the history ring's duration is rate-dependent and that guard math must be recomputed.

[MEDIUM] §9 bool ConsumeOnsetFlag() noexcept
CLAIM: bool ConsumeOnsetFlag() noexcept; // drives the trigger LED
PROBLEM: This is a test-and-clear on state written by the audio ISR and read by the firmware main loop, declared as a plain bool-returning method with no atomicity contract. The natural implementation (if (flag) { flag = false; return true; }) can be preempted by the audio ISR between the load and the store, losing an onset. It is also a single boolean, so onsets arriving faster than the main-loop poll rate coalesce into one — which directly undercuts the corpus rec it exists to satisfy (onset doc rec #7: a per-onset LED as the fix for "the Microcosm's single biggest documented complaint", silent undiagnosable trigger failure). During a fast strummed passage the LED under-reports exactly when the player most needs to see whether detection is working. The same gap applies in the other direction to Trigger(...) if it is ever called from a footswitch GPIO ISR.
FIX: Change the type and the contract: uint32_t ConsumeOnsetCount() noexcept implemented as a saturating std::atomic<uint32_t>::exchange(0) (or fetch_sub on a counter), documented as "callable from any thread; the audio thread only increments". Note in §4 that the LED driver should stretch each counted onset to a minimum visible duration so bursts remain individually readable. Add the same annotation to Trigger.

[MEDIUM] §9 dsp/ core API (whole block)
CLAIM: The API is presented as "the project's real ABI", with Process annotated "no alloc/locks/syscalls/exceptions/RTTI" and SetParam(ParamId, float, uint32_t sampleOffset = 0) described as "sample-accurate".
PROBLEM: No method other than SetSampleRate carries a thread annotation, and the mechanism the design most obviously needs is never described. sampleOffset is only meaningful relative to some block, so either (a) SetParam is called from inside the audio callback with offsets into the current block (the VST3/CLAP event-list model), or (b) it is called from the UI/pot thread and offsets refer to a future block, which requires a lock-free SPSC event queue with a stated capacity and overflow policy — neither of which exists in the doc. Tap(), SetFreeze(), SetGlobalReverse(), SetTempo(), SetSubdiv() and Trigger() share the ambiguity, and on the pedal they will be driven from a mix of main-loop polling and GPIO interrupts. For a header the doc explicitly calls the ABI, this is the largest specification hole in it.
FIX: Add a threading table to §9: for each method, the legal calling context (audio thread / any thread / non-RT only) and the mechanism (direct, atomic, queued). Specify the parameter/event queue concretely — SPSC ring, fixed capacity (e.g. 256 events), drop-oldest-or-coalesce on overflow — and define sampleOffset as either "frames from the start of the next Process call" or "frames from the start of the current block", not both. Mark PublishMode, Compile, Serialize, Validate, SaveState, LoadState non-RT explicitly.

[MEDIUM] §3 SDRAM access mitigations; §7 DTCM (T0 staging rings 2 KiB)
CLAIM: "SDRAM access mitigations, **all mandatory**... PLD prefetch one line ahead; **optionally** for T0, a small DTCM staging ring block-copied ahead of read time", budgeted in §7 as "T0 staging rings 2 [KiB]".
PROBLEM: 2 KiB across 8 T0 voices is 256 B per voice = 128 stereo int16 frames of source. A T0 grain must stage ceil(numFrames * ratio) + 3 source frames per block (cubic Hermite needs 4 taps). At the firmware's 48-frame block and ratio 4.0 (+24 st — the design's own Mosaic D and the Microcosm's "quad speed") that is 195 frames = 780 B per voice, 6.2 KiB total: 3x over budget. At the 256-frame block the accumulator is sized for, it is ~33 KiB: 16x over. The staging ring is undersized precisely for the pitched-up case that motivated the 32.32 phase format two paragraphs earlier. The row also contradicts itself — "all mandatory" followed by "optionally" in the same sentence — while the memory table budgets it as if present.
FIX: Size the row as a formula: tiers.T0 * (maxBlockSize * max_ratio + 4) * 4 B. Cap max_ratio explicitly — the design states no ratio ceiling anywhere; pick one (e.g. 4.0) and enforce it in ValidateMode — then re-total the DTCM table. Decide whether staging is mandatory or optional and say which; if optional, remove it from the budget and note the cost of enabling it.

[MEDIUM] §7 Memory plan (SDRAM row; microSD saves)
CLAIM: "Placement rules: only the history ring and looper touch SDRAM at audio rate... Loop-bearing presets go to microSD (required from v1)."
PROBLEM: Nothing in the design addresses D-cache/DMA coherency for the SD path, which the corpus flags twice for exactly this scenario (daisy-seed-platform.md: "any custom big buffers (e.g., SDRAM-resident grain buffers with DMA-driven SD-card streaming) need this handled correctly"). The corpus also verifies that libDaisy's own ConfigureMpu() maps the whole 64 MB SDRAM region CACHEABLE and BUFFERABLE (grain-delay-theory §5.1). So the CPU's writes into looper buffer B sit in dirty D-cache lines; an SDMMC DMA save started without SCB_CleanDCache_by_Addr over the region writes stale bytes to the card — intermittently and unreproducibly. The reverse (invalidate before a DMA load of a saved loop) is equally required, and an invalidate over a non-line-aligned range can corrupt adjacent CPU-owned data. Neither the memory plan nor the acceptance tests mention any of it.
FIX: Add a coherency rule to §7: SD transfers operate only on 32-byte-aligned, line-multiple SDRAM ranges; clean-by-address before every DMA write-out and invalidate-by-address before every DMA read-in, or stage through a small non-cacheable D2 SRAM bounce buffer. Add an acceptance test that saves and reloads a loop containing a known pattern and compares byte-for-byte after a cold power cycle.

[MEDIUM] §7 DTCM row ("128 KB, zero-wait", "~48" KiB used, "ISR stack 16")
CLAIM: The DTCM budget lists eight dsp/-owned items totalling ~48 KiB against "DTCM (128 KB, zero-wait)", with "ISR stack 16" as one of the line items, while §9 states the Arenas seam keeps dsp/ free of platform names.
PROBLEM: Two problems. (1) The stack is placed by the linker script, not handed to dsp/ as an arena base pointer — listing it in a table whose other rows are arena contents conflates two allocation mechanisms and will not survive contact with PlanMemory, which returns only bytes[3]/align[3]. (2) More seriously, the table implicitly treats the remaining ~80 KB of DTCM as free but accounts for zero bytes of libDaisy, DaisySP, FatFs/SDMMC, USB, MIDI, or the C runtime heap. On libDaisy's stock linker scripts, ordinary .data/.bss and the stack default to the DTCMRAM region — DSY_SRAM_BSS / DSY_SDRAM_BSS exist precisely because you must opt out of it. The corpus corroborates the direction ("DTCM ... Fast scratch data (stacks, hot buffers)") but does not quantify it, so the doc asserts headroom it has not established. If the assumption is wrong, the arena simply will not link.
FIX: Split the table into linker-managed rows (stack, platform .bss) and arena rows (Tier::Hot), and state the DTCM figure as "~32 KiB of dsp/ arena + 16 KiB stack, against whatever libDaisy leaves free — to be measured from the map file". Add "read the actual .map for DTCMRAM occupancy on a hello-world libDaisy build" to §10's hardware measurement gates alongside the DWT counters. If DTCM turns out tight, the 16 KiB window LUT is the obvious candidate to move to AXI.

[MEDIUM] §8 CPU budget (pessimistic column; excluded costs)
CLAIM: "Grain render, 64 voices... Pessimistic 3,200 (cache x2)" and "UI/MIDI/LED and coefficient recalc (sinf/powf) run at control rate and are not charged."
PROBLEM: Two understatements. (1) The corpus's miss model is explicitly derived at rate 1.0 ("one cache miss every 8 samples" for stereo int16 -> 8 misses/sample at 64 voices -> 320 cycles). Miss rate scales linearly with playback ratio, so at +24 st (ratio 4) the same 64 voices generate 32 misses/sample ~= 1,280 cycles at the corpus's 40-cycle working estimate and ~1,920 at its 60-cycle upper bound. The "x2" pessimism factor is therefore not a worst case for the mode the design markets hardest (Mosaic D's {-12, 0, +12, +24}); it is roughly the average case for it. (2) Excluding sinf/powf as "control rate" is wrong for this architecture specifically: §2's central structural commitment is that all mode interpretation happens in ScheduleGrain(), which resolves SemitonesToRatio (powf), equal-power pan (sin/cos) and per-grain filter coefficients — at trigger rate, inside Process. At 64 voices with 20 ms grains that is ~3,200 births/second. There is no line item for ScheduleGrain anywhere in the table, so the design's most novel component is the one thing not costed.
FIX: Re-derive the pessimistic grain-render column as a function of maximum ratio (state the ratio cap) rather than a flat x2, and note that the mitigation for high-ratio miss rates is the T0 staging ring — which then has to be sized per the finding above. Add an explicit ScheduleGrain row to §8 with a stated births-per-second worst case and a per-birth cycle estimate, and replace the transcendentals with LUT/polynomial approximations resolved at birth (a semitone LUT plus lerp, a pan LUT) so the cost is bounded and platform-independent — which also helps the cross-platform determinism contract.

## Lens 3: Product coverage and schema consistency

VERDICT: The engine architecture is coherent and the corpus citations are, with a few exceptions, honest — but the *product* layer is where this draft is thinnest, and the acid-test table is doing more rhetorical work than engineering work. Three structural gaps would bite immediately: (1) the 16-step table has fields for *when* and *what pitch* but no field for *where in the buffer* a step reads, which silently breaks Seq's "rearranged into new sequences", Arp's own advertised `step→k` addressing, and Pattern/Warp's rhythmic tap positions — five of eleven acid-test rows; (2) layers have a `voice_weight` but no level and no crossfade route, so Warp D ("taps cross-fade with grains") and Seq B ("fully CW adds a sustainer layer") cannot be expressed at all; (3) the Space knob's *delay* — half of a Microcosm front-panel control, documented in microcosm.md §2.5/§3/§11.4 — has vanished from the post chain, the memory plan, the CPU budget and the mode schema with no acknowledgement. The flagship JSON example is itself a counter-example to the design bet: `mosaic.d` maps Activity to `layers.0.voice_weight` on a single-layer mode, where weight is by definition inert, leaves `density` fixed at 0.55 (and density is anyway meaningless under a CLOCK source whose rate is the grid), and sources from a sliding `POS_LIVE`, so nothing in it produces "layers of short loops" or "the number of active loopers". Schema/API drift is pervasive but individually cheap to fix: `steps`, mode-level LFO/ENV sources, `mark_walk`, pin re-arm period, scale/root for `quantize`, per-entry pitch `weight`, and `RatioGen` are all named in prose and absent from the JSON; `sustain`, `links`, `ModeData` vs `ModeBlob`, `out_trim` vs `out_trim_db`, and `steal` are the reverse. The claim that "everything else is reused ≥ 3×" is refuted two sections earlier by the doc's own "POS_GRID — Seq is its only user". On coverage: of the corpus's five named six-year UX defects (microcosm.md rec #7), three are addressed and two — expression min/max range and footswitchable effect independent of the looper — are silently dropped ("expression" appears zero times in the document); the looper gets 46 MiB of SDRAM, a CPU line, and a front-panel knob, but zero API surface and zero parameters. Fix the step table, layer levels, and Space before the schema is frozen, and add an explicit "outside this document" section so the dropped wishlist items read as scoping rather than as oversight.

[HIGH] §4 Scheduler (trigger vocabulary) + §5 Coverage acid test
CLAIM: The CLOCK source advances "an optional 16-step table `{slot, ratio_idx, gain, mod_flags}`", and this table expresses Seq ("step table shuffle"), Arp ("MARK(step→k)"), Blocks, Pattern ("LIVE+tap table") and Warp.
PROBLEM: No field in the step entry addresses *position*. `slot` is a time slot on the clock grid, `ratio_idx` indexes the pitch set, `gain` and `mod_flags` are per-voice modifiers — so every step of a sequence reads from the same place in the buffer. That makes four acid-test rows unbuildable as written: Seq ("Short looping samples are **rearranged** into new rhythmic sequences", microcosm.md §4.1) cannot rearrange without a per-step `POS_GRID` slice index; Arp's advertised `step→k` addressing has no `k` field, so the arpeggio cannot walk the onset-mark ring per step; Pattern's four rhythmic tap *patterns* need per-tap delay times (a multi-tap at a fixed `base_ms` firing on a grid is just one delay retriggered, not four distinct patterns); Warp inherits the same defect. Separately, the `steps` object appears nowhere in the JSON example or any field list, so there is no schema for step count either — yet the Arp row says "step_count 2–8 = Activity" and Pattern's Activity is "number of active delay taps" (microcosm.md §4.4), both of which need a macro-addressable count. The Seq row also contradicts §4's own trigger table, which files Seq A under STOCHASTIC while the acid test files Seq under CLOCK, and no operator in the vocabulary performs "shuffle" (re-ordering) as distinct from `jitter` (off-grid smearing) or `intermittency` (skipping).
FIX: Add a position field to the step entry — e.g. `{slot, pos_sel, ratio_idx, gain, mod_flags}` where `pos_sel` is interpreted against the layer's position source (GRID slice index, MARK index k, or a per-tap ms offset for LIVE) — plus `steps.count`, `steps.order` (`fixed | shuffle | random`) and per-step `prob`. Publish the full `steps` schema in §5 with a second JSON example (seq.a or arp.b, not another single-layer LIVE mode), and reconcile the Seq row with the STOCHASTIC entry in the §4 trigger table.

[HIGH] §5 Modes as data (JSON example `mosaic.d`) + acid-test Mosaic row
CLAIM: "Mosaic | LIVE · CLOCK | ratio sets = octave subsets; Activity → voice_weight (1–8 \"loopers\")", realised in the JSON as a single layer with `voice_weight: 1.0`, `density: 0.55`, `position.source: "live"`, and a macro `activity → layers.0.voice_weight, range [1,8], curve 3.0`.
PROBLEM: The flagship example does not produce Mosaic. Three compounding defects: (a) §4 defines voice_weight as how "≤ 2 concurrent layers shar[e] the 64 slots by declared weight" — a *relative split*, so on a one-layer mode it is mathematically inert and the Activity knob does nothing, which is exactly the "Shape does nothing" class of defect the doc's own ValidateMode rule exists to prevent; (b) `density` is the only field that sets concurrency (`target = kMaxGrains · overlap³`), it is hard-coded at 0.55 (≈10.6 voices) and never bound to a macro, and under a CLOCK source the emission rate is the grid, not the density target, so density is doubly inert here; (c) microcosm.md §4.1 describes the Micro Loop family as "Layers of short **loops**" that repeat, but `POS_LIVE(d, spray)` reads d ms behind an advancing write head, so every grain sources fresh material and nothing loops. Since Mosaic is the corpus's "most famous effect — the sound people buy a Microcosm for", getting it wrong in the one worked example undermines the whole one-engine bet.

Add a loop/repeat mechanism for the Micro Loop family — either a `position.repeat` count that re-reads the same source region N times, or route Mosaic through `POS_PIN` with periodic re-arm — and state explicitly what governs concurrency when the trigger source is CLOCK (grid rate × grain size, with `density` documented as ignored or as a don't-fire ceiling).
